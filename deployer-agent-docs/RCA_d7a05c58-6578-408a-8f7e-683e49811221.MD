# RCA — stock-tracker-722 (prod) "server crashing / cannot calculate", dashboard zeros

## Problem statement
Right after a deploy, the live dashboard shows TOTAL TRANSACTIONS/PARTIES/PURCHASES/SALES = 0 and the Dead Items card shows "count unavailable — retry". Prod DB has ~500k transactions, so zeros = failing API calls, not empty data.

## Verdict: NOT an OOM. Root cause is MongoDB query/read TIMEOUTS.

### 1. Pod runtime evidence (OOM hypothesis — DISPROVEN)
- Active run `d7a05c58-6578-408a-8f7e-683e49811221`, both replicas: `phase=Running`, `ready=true`, **`restart_count=0`**, `state=running`.
- **No `OOMKilled`, no exit code 137, no CrashLoopBackOff** in pod events (looked back 120m).
- Only pod warnings: transient `Startup probe failed: HTTP probe failed with statuscode 503` during the 13:46–13:48 rollout boot — recovered, pods became Ready. Normal slow-boot, not a kill loop.
- Tier `tier_0` (Starter): **memory limit 512Mi**, request 200Mi; **CPU limit 250m**, request 50m; 2 replicas, HPA/VPA off. The container never approached a kill — memory ceiling is not the trigger.

### 2. Which image is live
- Deploy COMPLETED. Active = run `d7a05c58...`, `run_status=success`, completed 2026-10-10T13:48:19Z, image tag `stock-tracker-722:d7a05c58-6578-408a-8f7e-683e49811221`. The newest "Dead Items" code IS live — deploy did not fail.

### 3. Backend logs — the actual failure
Filtered logs on the active run show the 500s are DB timeouts, two flavors:
- **Server-side maxTimeMS:** `pymongo.errors.ExecutionTimeout: Executor error during find command: stock-tracker-722-test_database.historical_transactions :: caused by :: operation exceeded time limit ... code 50, codeName 'MaxTimeMSExpired'` — on a **find** against `historical_transactions`.
- **Client-side socket read timeout:** repeated `pymongo.errors.NetworkTimeout: customer-apps-shard-00-02...mongodb.net:27017: The read operation timed out` / `TimeoutError: The read operation timed out`.
- These surface as HTTP 500 on `/api/stats`, `/api/stamp-verification/history`, `/api/analytics/dead-items`, `/api/analytics/dead-items/summary` (status histogram: 20×500 in-window). The frontend catches the 500s and falls back to zeros / "count unavailable".
- No `MemoryError`, no OOM trace anywhere in logs.

### 4. DB binding / data-loss check — INTACT
- `db_name = stock-tracker-722-test_database`, 37 collections present including `transactions` and `historical_transactions`.
- `transactions` count = **559,317** (~500k confirmed). `historical_transactions` count = **219,833**.
- "Data missing after deploy" is ruled out — the data is there; the zeros are purely the 500s.

### Why it times out (supporting detail)
- `transactions` indexes: `_id`, `{item_name,type}`, `{date}`, `{date,type}`, `{date,party_name,type}`.
- `historical_transactions` indexes: `_id`, `{historical_year,type}`, `{item_name,type}`, `{batch_id}` — **no `date` index**. The timed-out find is on `historical_transactions`.
- The Dead Items report scans the full history (559k + 219k docs) in quarter chunks and accumulates per-day balance dicts / identity sets in Python per item. On tier_0's **250m CPU** that heavy scan+compute is slow enough to blow past both the pymongo socket timeout and the server `maxTimeMS`, so every call 500s. Low CPU is a contributing amplifier, not the kill cause.

## Fixes
1. **CODE (E1 redeploy):** This is a query-efficiency problem, not a Python memory profile. Primary fix:
   - Push the Dead Items / stats computation into MongoDB aggregation pipelines (`$group`/`$match` server-side with `allowDiskUse=true`) instead of pulling full history into Python; bound every query by date window and paginate.
   - Add an index on `historical_transactions` matching the failing find's filter/sort (e.g. a `date` or `{date,type}` index) so the `MaxTimeMSExpired` find is index-backed.
   - Raise the pymongo client timeouts (socketTimeoutMS / serverSelectionTimeoutMS) and set a sane per-query `maxTimeMS` once the queries are bounded, so a legitimately long report does not hit the current socket read timeout.
   - Reproduction note: the live-DB timeout at 500k-doc scale CANNOT be reproduced in the eph sandbox (no prod data, more generous resources), so this was NOT sandbox-verified — diagnosis is from prod logs + pod events + live DB counts.
2. **USER (optional, contributing):** tier_0 gives only 250m CPU, which slows the heavy aggregation and helps push it past the timeout. Raising the tier (Resources tab) will speed the compute, but it is a mitigation — without the code/query fix the scans can still time out at scale. Fix the queries first.
