# RCA — "Failed to load dead items" on production /dead-items

## Problem statement
Live app shows toast "Failed to load dead items" on `/dead-items`. The page renders but the data fetch `GET /api/analytics/dead-items` (admin JWT) fails. Works in preview (200 in 0.3s), fails only in production. A redeploy was initiated just before the report.

## What I verified

### 1. Deployment finished; live backend IS running the newest code — NOT a stale build
- Active run = `1f98fa41-69cd-472b-bddf-77419822f4fa`, status **success**, completed 2026-10-10T08:07:54Z. It is the run currently serving traffic.
- The route exists on the live pod: `GET /api/analytics/dead-items` returns **403 `{"detail":"Not authenticated"}`** (437ms) when called without a JWT — a 404 would indicate an old build. So hypothesis #1 (stale backend → 404) is **ruled out**.
- New code booted cleanly: startup log line present — `server - INFO - Seeded stock_sale_baseline: 358 items as on 2022-12-21`. Production DB confirms `stock_sale_baseline` = **358 docs**. Seeding is fine; hypothesis #3 ruled out.

### 2. Confirmed cause — the aggregation in get_dead_items times out at the MongoDB layer → 500
Backend logs for the active run show the route returning **500 Internal Server Error** (×2), each with this traceback:

```
Traceback (most recent call last):
  ...
  File "/app/backend/server.py", line 5403, in get_dead_items
  File "/app/backend/server.py", line 5387, in _consume
    async for d in coll.aggregate(pipe):
  ...
  File ".../pymongo/network.py", line 328, in _receive_data_on_socket
    raise NetworkTimeout(msg) from error
TimeoutError: The read operation timed out
```
A second variant shows `raise ExecutionTimeout(...)` from `_check_command_response` — i.e. the server-side aggregation also hit an execution time limit. The failure is inside the `coll.aggregate(pipe)` iteration in `get_dead_items`.

### 3. Why prod only — data scale
- Production `transactions` collection = **552,889 documents** (reported ~200k; actual is higher).
- Preview has a tiny dataset, so the same pipeline returns 200 in 0.3s there. At 552k docs in prod the aggregation does not return within the driver read timeout / server execution timeout and the request 500s.
- Existing indexes on `transactions`: `_id_`, `type_1_item_name_1`, `date_1`, `date_1_type_1`, `date_1_type_1_party_name_1`. Despite these, the dead-items pipeline is not completing in time — likely a full-collection scan/group stage not served by an index, and/or no `maxTimeMS`/pagination.

## Observed answers to the reporter's questions
- Deployment status / build: **live and up to date** — active run `1f98fa41…`, image tag `…:1f98fa41-69cd-472b-bddf-77419822f4fa`, succeeded 2026-10-10T08:07:54Z.
- HTTP status + latency of live `/api/analytics/dead-items`: **403** in 437ms unauthenticated (route present); **500 Internal Server Error** when exercised with a valid admin JWT, caused by a MongoDB read/execution timeout (the aggregation does not complete).
- Related log lines: the `get_dead_items` traceback above; `Seeded stock_sale_baseline: 358 items as on 2022-12-21` (new code booted).

## Root cause
`GET /api/analytics/dead-items` runs a MongoDB aggregation (`server.py` ~line 5387/5403, `get_dead_items` → `_consume`) over the full 552k-document `transactions` collection. At production scale it exceeds the Mongo driver/server timeout and raises `NetworkTimeout`/`ExecutionTimeout`, so FastAPI returns 500 and the frontend shows the "Failed to load dead items" toast. This is a query-performance / code issue, not a deploy, secret, tier (no OOM), or DNS problem.

## Suggested fix (Code — E1)
Optimize the dead-items aggregation for prod-scale data in `/app/backend/server.py` (`get_dead_items`), e.g.:
- Ensure the `$match`/`$group` stages are backed by an index (add a compound index matching the pipeline's filter+group keys if the current ones don't serve it); push filtering before grouping.
- Reduce scanned volume (date-window the baseline-vs-current comparison, precompute/cache the dead-items result, or compute incrementally against `stock_sale_baseline`).
- As a safety net, set a sane `maxTimeMS` and return a graceful error instead of an unhandled 500.

Could not reproduce in the eph sandbox: it has no production DB (552k transactions) and no admin JWT, so this live-data timeout is not reproducible there. Diagnosis is from the live run's traceback + prod DB counts/indexes above.
